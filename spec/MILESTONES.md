# MILESTONES.md — אבני דרך לפיתוח הפרויקט One Joke

מסמך זה מגדיר את אבני הדרך (Milestones) המרכזיות לפיתוח אפליקציית ה-Web וה-PWA של **One Joke**, בהתבסס על מסמכי **PRD.md**, **ARCHITECTURE.md** ו-**DESIGN.md**.

הפיתוח מחולק ל-Vertical Slices ברורים, משמעותיים וניתנים לבדיקה עצמאית, כך שכל אבן דרך מוסיפה יכולת משתמש עובדת מקצה לקצה או תשתית קריטית הנחוצה להמשך.

---

## כללי ביצוע הפיתוח – Development Execution Rules

> **הנחיה מחייבת ל-AI / גורם הפיתוח:**
> 1. יש לפתח את ה-Milestones לפי הסדר המוגדר במסמך זה בלבד.
> 2. לאחר השלמת כל Milestone, יש לעצור את הפיתוח, להציג למשתמש את התוצר שהושלם ואת תוצאות הבדיקות מול ה-Definition of Done.
> 3. **אין להתחיל בפיתוח ה-Milestone הבא ללא אישור מפורש של המשתמש.**

## פירוט אבני הדרך (Milestone Details)

### Milestone 1: Project Setup, Environments & Base Design System ✅

#### שם ומטרה
- **שם:** הקמת תשתית הפרויקט, הגדרת סביבות עבודה ושפה עיצובית בסיסית.
- **מטרה:** להקים את Repository הקוד, להגדיר את סביבת הפיתוח בענן (Supabase Development), להגדיר את השפה העיצובית (RTL, גופנים, צבעים) ולהכין את שלד ה-PWA הנדרש למובייל. Vercel מחובר ב-M5, ופרויקט Supabase Production נוצר ב-M5 (ARCHITECTURE 9.5).

#### מה יש לממש
- הקמת פרויקט Next.js עם App Router ו-TypeScript.
- הגדרת תמיכה מלאה ב-RTL ובשפה העברית (`lang="he"`, `dir="rtl"`).
- טעינת הגופנים Heebo (עברית) ו-Inter (אנגלית), והגדרת משתני עיצוב (CSS Variables) לפי פלטת הצבעים והטיפוגרפיה המוגדרים ב-DESIGN.md (`#3B82F6`, `#FACC15`, `#EF4444`, `#111827`, וכו').
- יצירת הדרכה צעד-אחר-צעד והקמת פרויקט Supabase **Development**. פרויקט **Production** נוצר רק ב-M5, כדי שלא יושהה בתוכנית החינמית לפני שמשתמשים בו.
- הגדרת משתני סביבה (`.env` לפיתוח מקומי מול Supabase Development בלבד — ADR-1).
- יצירת Manifest בסיסי עבור PWA (`app/manifest.ts` — ADR-2) עם תמיכה בתצוגת `standalone`, צבעי ערכת נושא ואייקונים ייעודיים למובייל.
- יצירת מנגנון בדיקת תקינות המודל המוגדר ב-`OPENAI_MODEL` (GPT-5) בעת הפעלת השרת.

#### תוצר מצופה
שלד אפליקציה עובד ב-Next.js המציג מסך בית בסיסי מעוצב ב-RTL לפי ה-Style Guide, המחובר לסביבת Supabase Development ומותקן כ-PWA במסכים תומכים.

#### Definition of Done
1. פרויקט Next.js עולה ריצה מקומית (`npm run dev`) ללא שגיאות compilation או TypeScript.
2. הוקם פרויקט Supabase Development, ומשתני הסביבה המקומיים מופנים אך ורק אליו.
3. הגופנים Heebo ו-Inter נטענים כראוי, והגדרות RTL פועלות באופן תקין בדפדפן.
4. קובץ ה-Manifest של ה-PWA נטען בהצלחה ומזוהה ע"י Chrome DevTools / Lighthouse.
5. הוגדר קובץ `.env.example` הכולל את כל שמות המשתנים הנדרשים ללא ערכים סודיים, וקובץ `.env` (וכל `.env.*`) מוחרג ב-`.gitignore`.

### Milestone 2: Anonymous Session, App Shell & Privacy Page ✅

#### שם ומטרה
- **שם:** זיהוי אנונימי של מכשירים, שלד האפליקציה ודף הפרטיות.
- **מטרה:** שכל מי שנכנס לאתר יקבל ברקע זיהוי אנונימי של המכשיר (בלי התחברות ובלי מסך התחברות), ושהאתר ייפתח ישירות בשלד של מסך היצירה, עם קישור לדף הפרטיות.

#### מה יש לממש
- **הדרכה צעד-אחר-צעד:** הפעלת **Allow anonymous sign-ins** בהגדרות Auth של פרויקט Supabase **Development** (ARCHITECTURE 7.1, 9.4).
- התקנת `@supabase/supabase-js` ו-`@supabase/ssr`, ומימוש Supabase SSR Helpers לניהול session ב-Cookies מאובטחים.
- **Proxy/Middleware של Next.js:** יצירה אוטומטית של משתמש אנונימי (`signInAnonymously`) כשאין session, ורענון session שפג. המשתמש אינו רואה דבר.
- **סרגל עליון:** הלוגו „JOKE” בלבד (DESIGN, מבנה משותף).
- **מסך יצירת בדיחה (Screen 1.9) — פריסה בלבד:** איור, כותרת „מוכנים לבדיחה?”, הסבר, שדה נושא עם Placeholder ומונה תווים (עד 100), כפתור „צרו בדיחה” וקישור „פרטיות” (DESIGN 2.6). הכפתור עדיין אינו יוצר בדיחה (M4). מחליף את מסך הבית הזמני של M1.
- **דף פרטיות (Screen 1.10):** דף טקסט קצר לפי PRD 4.א.8. הנוסח מוצג למשתמש לאישור.

#### תוצר מצופה
האתר נפתח ישירות במסך היצירה, בלי שום התחברות. ברקע נוצר זיהוי אנונימי למכשיר, שנשמר בין רענונים. דף הפרטיות זמין מהקישור בתחתית המסך.

#### Definition of Done
1. כניסה ראשונה לאתר יוצרת session אנונימי ב-Supabase Development, בלי מסך התחברות ובלי פעולה של המשתמש (נבדק ברשימת המשתמשים ב-Supabase: מופיע משתמש Anonymous).
2. רענון הדף וסגירה ופתיחה של הדפדפן שומרים על אותו זיהוי (לא נוצר משתמש חדש בכל כניסה).
3. אין באתר מסך התחברות, מסך פרופיל, תפריט או סרגל ניווט תחתון.
4. מסך היצירה (1.9) מוצג לפי DESIGN, כולל מונה התווים והגבלת 100 התווים בשדה.
5. דף הפרטיות נפתח מהקישור, ונוסחו הוצג למשתמש.
6. הבדיקות נערכו מול סביבת Supabase Development בלבד.

### Milestone 3: Database Schema & Atomic Quota ✅

#### שם ומטרה
- **שם:** מנגנון ניהול ואכיפת מכסה יומית ותקרה יומית, אטומיים, ב-Database.
- **מטרה:** להבטיח אכיפה מדויקת ואטומית של 10 בדיחות ביום לכל מכשיר ו-300 ביום לכל האתר, לפי שעון ישראל (`Asia/Jerusalem`), ומניעת עקיפה בבקשות מקבילות.

#### מה יש לממש
- יצירת קובץ Database Migration ב-`supabase/migrations/` הכולל:
  - טבלת `daily_usage` (`user_id`, `usage_date`, `count`, `updated_at`) עם אילוץ `UNIQUE (user_id, usage_date)`.
  - טבלת `site_daily_usage` (`usage_date`, `count`, `updated_at`) — ARCHITECTURE 5.1א.
  - טבלת `generation_reservations` (`id`, `user_id`, `usage_date`, `status`, `created_at`) — ARCHITECTURE 5.1ב.
  - הגדרת Row Level Security (RLS) המונעת גישת כתיבה ישירה מהלקוח. מותרת קריאה של שורות `daily_usage` של המכשיר עצמו בלבד.
  - ארבע פונקציות PostgreSQL (ARCHITECTURE 5.2), **ללא פרמטרים של משתמש או תאריך**: `reserve_joke_generation()` (מגדילה את מונה המכשיר רק אם `count < 10` ואת מונה האתר רק אם `count < 300`, באותה טרנזקציה), `complete_joke_generation(reservation_id)`, `release_joke_generation(reservation_id)` ו-`get_quota_status()`. המכשיר נקבע לפי `auth.uid()`, והתאריך לפי `Asia/Jerusalem` בתוך מסד הנתונים.
- התקנת Supabase CLI וחיבורו לפרויקט **Development** (הדרכה צעד-אחר-צעד), והרצת ה-Migration על סביבת **Supabase Development בענן**.
- הכנת GitHub Actions workflow להרצת Migrations ב-Production בהפעלה ידנית בלבד (ARCHITECTURE 9.3, ADR-5). ה-workflow רק נכתב בשלב זה; הוא לא מופעל, ואין צורך עדיין בסודות של Production.
- בדיקות יחידה אוטומטיות (Vitest) למכסה ולתקרה, כולל חצות ומעבר בין שעון קיץ לשעון חורף.
- הצגת „נשארו X מתוך 10 היום” במסך היצירה, לפי `get_quota_status()` (DESIGN 1.9).

#### תוצר מצופה
בסיס נתונים מעודכן בסביבת Development עם מנגנון שריון מכסה ותקרה אטומי, שעובד ונבדק, ומסך היצירה מציג כמה בדיחות נשארו למכשיר.

#### Definition of Done
1. קובץ ה-Migration נשמר ב-Git והורץ בהצלחה מול סביבת Supabase Development בענן.
2. `reserve_joke_generation` מאשרת את 10 הבקשות הראשונות ביום ממכשיר אחד, ודוחה את ה-11 (`DEVICE_LIMIT`).
3. אחרי 300 שריונים באתר כולו באותו יום, `reserve_joke_generation` דוחה בקשות מכל מכשיר (`SITE_LIMIT`), גם ממכשיר שעוד לא הגיע ל-10.
4. בדיקת בקשות מקבילות מוכיחה כי המנגנון האטומי מונע חריגה מ-10 למכשיר ומ-300 לאתר.
5. איפוס המכסה והתקרה פועל כראוי בבדיקת מעבר התאריך בחצות לפי שעון ישראל (`Asia/Jerusalem`).
6. `release_joke_generation` מחזירה את המקום במכסה ובתקרה פעם אחת בלבד, ואינה משפיעה על שריון שכבר הושלם.
7. קריאה ישירה לפונקציות אינה מאפשרת לבחור תאריך או מכשיר אחר, ואינה מאפשרת לחרוג מהמכסה או מהתקרה.
8. מסך היצירה מציג „נשארו X מתוך 10 היום” לפי הנתונים במסד הנתונים.
9. קובץ ה-workflow להרצת Migrations ב-Production נשמר ב-Git, ומוגדר להפעלה ידנית בלבד.

### Milestone 4: AI Joke Generation Engine & Main User Flow ✅

#### שם ומטרה
- **שם:** מנוע יצירת בדיחות ב-AI (GPT-5) וזרימת משתמש מרכזית מקצה לקצה.
- **מטרה:** לאפשר לכל מי שנכנס להזין נושא (או להשאיר ריק), לקבל בדיחה בעברית מ-GPT-5, לראות מצבי טעינה, ולטפל במצבי שגיאה ומיצוי מכסה.

#### מה יש לממש
- **Next.js Route Handler (`POST /api/jokes`):**
  - אימות ה-Session האנונימי.
  - נירמול ואימות הקלט (`topic`): מחרוזת, עד 100 תווים.
  - הוראות למודל לפי ARCHITECTURE 6.3: בדיחה בעברית עד 4 שורות, נקייה ולא פוגענית, והנושא מועבר כנתון בלבד. תשובה ריקה, בלי אותיות עבריות או ארוכה מדי נחשבת כשל.
  - שריון מכסה אטומי מול ה-Database (באמצעות המנגנון מ-M3): `complete` אחרי בדיחה תקינה, ו-`release` אחרי כשל או חריגת זמן.
  - קריאה בצד השרת בלבד ל-OpenAI API עם מודל GPT-5 (`OPENAI_MODEL`), קבלת בדיחה קצרה בעברית, עם רמת חשיבה מינימלית ומגבלת זמן של כ-20 שניות (ARCHITECTURE 6.3).
  - הגדרת `maxDuration` של הפונקציה ב-Vercel ל-30 שניות לפחות.
- זמן המתנה בלקוח: אחרי 25 שניות בלי תשובה מוצג מסך השגיאה.
- בדיקות יחידה עם session ותשובות OpenAI מדומים: הצלחה, כשל, חריגת זמן, מכסת מכשיר ותקרת אתר.
- **מסך יצירת בדיחה (Screen 1.9):** חיבור הכפתור „צרו בדיחה” ליצירה בפועל.
- **מסך טעינה (Screen 1.4):** חיווי מונפש עם הטקסט „מכינים לכם בדיחה...”.
- **מסך הצגת בדיחה (Screen 1.3):** כרטיס תוכן המציג בדיחה אחת בלבד בעברית, כפתור „בדיחה נוספת” (אותו נושא), כפתור משני „נושא אחר” (חזרה למסך היצירה) ו„נשארו X מתוך 10 היום”. אחרי הבדיחה העשירית — הודעה במקום הכפתורים (DESIGN 1.3).
- **מסך מכסה יומית שמוצתה (Screen 1.5):** אייקון לוח שנה, כותרת „הגעתם למכסה היומית” וטקסט „אפשר לחזור מחר.”. מוצג גם כשמכסת המכשיר מוצתה וגם כשתקרת האתר מוצתה, וגם במקום מסך היצירה כשנכנסים אחרי המיצוי.
- **מסך שגיאה ביצירת בדיחה (Screen 1.6):** אייקון אזהרה, כותרת „אירעה שגיאה”, טקסט הסבר וכפתור „נסו שוב”.

#### תוצר מצופה
אפליקציה עובדת מקצה לקצה, בלי התחברות: מי שנכנס מזין נושא, רואה מסך טעינה, מקבל בדיחה בעברית מ-GPT-5, ויכול לבקש בדיחות נוספות עד למיצוי המכסה או לקבלת הודעת שגיאה מתאימה.

#### Definition of Done
1. הזנת נושא מחזירה בדיחה בעברית הקשורה לנושא; שדה ריק מחזיר בדיחה כללית בעברית.
2. ה-API Key של OpenAI מנוהל בשרת בלבד ואינו נחשף בשום שלב לדפדפן/לקוח.
3. בכל רגע מוצגת בדיחה אחת בלבד, ובדיחה חדשה מחליפה לחלוטין את הקודמת (אין שמירת היסטוריה).
4. בזמן יצירת הבדיחה מוצג מסך הטעינה (Screen 1.4).
5. אחרי הבדיחה העשירית מוצגת ההודעה על סיום המכסה במקום „בדיחה נוספת”; כניסה חוזרת מציגה את מסך המכסה (Screen 1.5); וקריאות נוספות ל-OpenAI נחסמות.
6. כשתקרת האתר מוצתה, כל מכשיר מקבל את מסך המכסה ואין קריאה ל-OpenAI.
7. כשל ברשת או ב-API מציג את מסך השגיאה (Screen 1.6) עם כפתור „נסו שוב”.
8. ניסיון שנכשל (שגיאה, תשובה ריקה או חריגת זמן) אינו מוריד מהמכסה הנותרת.
9. אם לא התקבלה בדיחה תוך 25 שניות, מוצג מסך השגיאה.
10. „בדיחה נוספת” מחזירה בדיחה באותו נושא, ו„נושא אחר” מחזיר למסך היצירה.
11. נושא ארוך מ-100 תווים נחסם בשדה ונדחה בשרת.

### Milestone 5: Edge Cases, PWA Finalization, E2E Testing & Production Deployment

#### שם ומטרה
- **שם:** טיפול במקרי קצה, השלמת PWA, בדיקות מקיפות ופריסה מלאה לסביבת Production.
- **מטרה:** להביא את המוצר לרמת מוכנות מלאה להשקה (Production Ready), לבצע בדיקות מקיפות, להקים את Production, להריץ Migrations ב-Production ולפרוס ב-Vercel.

#### מה יש לממש
- **טיפול במקרי קצה:**
  - מניעת לחיצות כפולות (Debounce/Disable) על כפתור „צרו בדיחה”.
  - טיפול בניתוק אינטרנט/אובדן תקשורת תוך כדי בקשה.
  - session אנונימי שנמחק או פג באמצע שימוש: יצירה מחדש ברקע וניסיון חוזר (ARCHITECTURE 6.1).
  - סניטציה של קלט הנושא (מגבלת 100 התווים נבנית כבר ב-M2/M4).
- **השלמת PWA:** בדיקת התקנה על מכשירי iOS ו-Android אמיתיים, ווידוא תצוגת Standalone תקינה ללא סרגלי דפדפן.
- **דף פרטיות:** אישור סופי של הנוסח על ידי המשתמש לפני העלייה לאוויר.
- **בדיקות אוטומטיות:** Playwright לזרימה המלאה מול Development (אין התחברות, ולכן אפשר לבדוק את כל הזרימה), עם מספר קטן של קריאות אמיתיות ל-OpenAI בכל הרצה; ו-Vitest למכסה, לתקרה ולשגיאות עם תשובות מדומות (ARCHITECTURE 9.2).
- **תהליך פריסה ל-Production (צעד-אחר-צעד):**
  1. קבלת אישור מפורש מהמשתמש לפריסת Production, כולל החלטה אם לעבור לתוכנית בתשלום (PRD 5.ב).
  2. הדרכת המשתמש ליצור את פרויקט Supabase **Production**, להפעיל בו **Allow anonymous sign-ins** ולהגדיר את כתובת האתר.
  3. הדרכת המשתמש להזין את סודות Production ב-GitHub Secrets, ולהפעיל בלחיצה את ה-workflow שמריץ את ה-Database Migrations מול פרויקט **Supabase Production** בענן (ADR-5).
  4. חיבור ה-Repository ל-Vercel, והגדרת משתני הסביבה (OpenAI Key, Supabase Prod Keys) ב-Vercel Production, ומשתני Preview מול Development בלבד.
  5. ביצוע Production Deployment מ-GitHub ל-Vercel.

#### תוצר מצופה
אפליקציה באוויר ב-Production, מותקנת כ-PWA, עובדת באופן מלא ומאובטח מול פרויקט Supabase Production ו-Vercel, בלי התחברות.

#### Definition of Done
1. כל בדיקות ה-Unit וה-E2E עוברות בהצלחה.
2. ה-Database Migrations הורצו בהצלחה בסביבת Supabase Production דרך ה-workflow ב-GitHub, **לאחר קבלת אישור מפורש מהמשתמש**.
3. האפליקציה פרוסה ב-Vercel Production ומחוברת לסביבת ה-Production של Supabase בלבד.
4. בדיקת התקנת PWA עובדת בהצלחה במכשיר נייד.
5. בדיקת שרשרת מלאה ב-Production: כניסה לאתר בלי התחברות, יצירת בדיחה, ומיצוי מכסה — פועלים ללא שגיאות.
6. נוסח דף הפרטיות אושר על ידי המשתמש ומופיע באתר החי.
