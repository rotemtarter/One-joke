# ARCHITECTURE.md — ארכיטקטורה טכנית

## 1. מטרת המסמך והנחות יסוד

מסמך זה מתרגם את דרישות `PRD.md` של מערכת ליצירת בדיחות באמצעות AI לתכנון טכני בר־מימוש. המוצר הוא אתר Web בעברית, מותאם למובייל וניתן להתקנה כ־PWA. **אין התחברות:** כל מי שנכנס יכול לבקש בדיחה בעברית בנושא לבחירתו או בדיחה כללית. כל מכשיר מזוהה באופן אנונימי ואוטומטי, ומוגבל לעד 10 בדיחות ביום קלנדרי לפי שעון ישראל; האתר כולו מוגבל לעד 300 בדיחות ביום. בכל רגע מוצגת בדיחה אחת בלבד; אין היסטוריית בדיחות.

ה־PRD קובע שימוש ב־GPT-5, ביצוע קריאות AI בצד השרת בלבד, שמירת מוני השימוש ב־Database ואכיפת המכסה בשרת. הוא אינו מגדיר ספקי תשתית. הבחירות להלן הן החלטות ארכיטקטוניות לצורך מימוש פשוט ותחזוקתי, ולא שינוי בדרישות המוצר.

### 2.1 נימוקי הבחירה

- **Next.js + TypeScript + Vercel:** המוצר דורש גם UI וגם נקודת Backend מאובטחת שמפעילה את OpenAI. Next.js מאפשר לרכז אותם באפליקציה אחת, ו־Vercel מתאימה להרצת Next.js ולפריסה אוטומטית מ־GitHub. אין צורך להקים שרת Backend נפרד.
- **Supabase Anonymous Sign-Ins + PostgreSQL:** משתמש אנונימי של Supabase הוא משתמש רגיל מבחינת מסד הנתונים (יש לו `auth.uid()`), אבל נוצר בלי שום פרט מזהה ובלי מסך התחברות. כך כל מנגנון המכסה האטומי (סעיף 5) נשאר זהה, וה־session נשמר ב־cookie מאובטח. PostgreSQL מתאים למונה יומי ייחודי לכל מכשיר ולתקרה כללית, לאילוץ `UNIQUE` ולאכיפה אטומית גם בבקשות מקבילות.
- **OpenAI API:** נדרש על פי ה־PRD, והקריאה מתבצעת רק ב־Backend. יש לקבע את מזהה המודל לפי ההחלטה המוצרית ולבדוק זמינות ומצב תמיכה לפני העלייה לאוויר.
- **PWA ללא שכבת Offline מורכבת:** דרישת המוצר היא התקנה במכשירים תומכים, לא שימוש מלא ללא חיבור. יצירת בדיחה דורשת רשת ולכן אין לשמור או להציג תוצאה מדומה במצב Offline.
- **ללא Storage, Queue, Analytics או שירותי AI נוספים:** אין ב־PRD העלאת קבצים, היסטוריה, משימות רקע, אנליטיקה או תוכן מדיה. רכיבים כאלה יוסיפו עלות ומורכבות ללא צורך נוכחי.

### 2.2 חלופות שנבחנו בקצרה

- **Frontend/Backend:** React עם Vite ו־Backend נפרד, או Next.js. נבחר Next.js כדי לצמצם שירותים ו־Repositories ולשמור את מפתח OpenAI בצד השרת.
- **Hosting:** GitHub Pages מתאים לאתר סטטי, אך אינו מתאים לבדו לדרישת Backend שמבצע קריאות AI מאובטחות ואוכף מכסה. נבחר Vercel עבור Next.js.
- **זיהוי מכשיר:** cookie אקראי שהאפליקציה מנהלת בעצמה, לעומת Supabase Anonymous Sign-Ins. נבחר Supabase, כי הוא מספק session חתום ומאובטח ו־`auth.uid()` שמסד הנתונים סומך עליו, בלי לכתוב מנגנון חתימה עצמאי, ושומר על פונקציות המכסה בלי שינוי.
- **PWA:** PWA בסיסית עם Manifest לעומת פתרון Offline מלא. נבחרת האפשרות הבסיסית, משום שיצירת בדיחה תלויה ב־Backend וב־OpenAI.

### 2.3 מגבלות וסיכונים

1. **זמינות GPT-5:** קטלוג המודלים והתיעוד של OpenAI משתנים. נכון למועד המחקר, דפי OpenAI מסמנים חלק ממזהי GPT-5 הישנים או ממשפחת GPT-5 כ־Deprecated ומפרסמים מועדי הסרה למודלים מסוימים. לכן יש לאמת בחשבון ה־API את מזהה המודל המדויק שמותר לשימוש. אין להחליף מודל אוטומטית, משום שה־PRD דורש GPT-5; אם המזהה הנדרש אינו זמין, יש לקבל החלטה מוצרית מפורשת לפני החלפה.
2. **עלויות משתנות:** OpenAI מחייבת לפי מודל ושימוש; Supabase ו־Vercel מגבילים משאבים לפי תוכנית. יש להגדיר התראות שימוש ותקציב ב־OpenAI ולבדוק את התמחור לפני השקה. התקרה היומית של האתר (300) מגבילה את העלות המרבית ליום.
3. **תוכנית חינמית של Supabase:** התוכנית החינמית מאפשרת שני פרויקטים פעילים בסך הכול לפי תנאי החשבון/הארגון, אך פרויקטים Free עם פעילות נמוכה עשויים להושהות אוטומטית לאחר כשבוע. לכן היא יכולה להתאים לפיתוח ראשוני, אך אינה בחירה בטוחה ל־Production שצריך להיות זמין באופן רציף.
4. **מגבלות Functions:** יש להגדיר Timeout סביר ל־Backend ולתאם אותו עם זמן התגובה של OpenAI. אין לבצע עיבוד כבד או משימות רקע, שאינם נדרשים למוצר.
5. **עקיפת המכסה למכשיר:** מחיקת cookies, חלון גלישה בסתר או סקריפט שיוצר משתמשים אנונימיים חדשים מקבלים מכסה חדשה. זו מגבלה מודעת (PRD 4.א.1). ההגנות: מגבלת הקצב של Supabase על יצירת משתמשים אנונימיים לפי כתובת IP, ו**התקרה הכללית של האתר**, שחוסמת את העלות גם אם המכסה למכשיר נעקפת. CAPTCHA (למשל Cloudflare Turnstile) לא נכלל בגרסה הראשונה, ויתווסף רק אם יתגלה שימוש לרעה.
6. **משתמשים אנונימיים מצטברים:** כל מכשיר חדש יוצר רשומה ב־`auth.users`. בנפחים של מוצר אישי זה זניח; ניקוי תקופתי של משתמשים אנונימיים ישנים אינו נדרש בגרסה הראשונה.
7. **שינויי סכימה:** שינויים ב־Database חייבים לעבור דרך Migration files. אין לבצע שינויים ידניים ישירות ב־Production לאחר אימוץ תהליך migrations.

## 3. ארכיטקטורת המערכת

### 3.1 מבט כללי

```text
משתמש במכשיר נייד
        |
        | HTTPS
        v
Next.js PWA (Vercel)
  |                         |
  | Anonymous sign-in       | POST /api/jokes
  | (אוטומטי, ברקע)          v
  v                      Next.js Route Handler
Supabase Auth               |
                            | אימות session אנונימי / JWT
                            | שריון אטומי: מכסת מכשיר + תקרת אתר
                            v
                       Supabase PostgreSQL
                            |
                            | אם נותרה מכסה
                            v
                       OpenAI API (GPT-5)
                            |
                            | טקסט בדיחה בעברית
                            v
                    תשובת API לממשק
```

האפליקציה היא **Modular Monolith** קטן: פרויקט Next.js אחד שמכיל את ה־UI ואת ה־Backend endpoints. Supabase מנוהל כשירות חיצוני. אין צורך ב־microservices או בשרת Backend נפרד.

### 3.2 אחריות הרכיבים

**Frontend**
- מציג את מסך יצירת הבדיחה ישירות, בעברית וב־RTL. אין מסך התחברות.
- מציג שדה נושא, כפתור יצירה, מספר הבדיחות שנותרו, חיווי טעינה, תוצאה אחת בכל רגע והודעות שגיאה/מכסה.
- שולח בקשות ל־Backend ומציג רק את הבדיחה האחרונה שהתקבלה; אין לשמור היסטוריית בדיחות.
- מונע לחיצות כפולות בממשק לשיפור UX, אך אינו מסתמך על כך כאמצעי אבטחה או אכיפת מכסה.

**Session אנונימי (Proxy/Middleware של Next.js)**
- בכל בקשה לדף או ל־API, מוודא שקיים session של Supabase ב־cookies. אם אין, יוצר משתמש אנונימי (`signInAnonymously`) ושומר את ה־session ב־cookie מאובטח. המשתמש אינו רואה דבר.
- מרענן session שפג, לפי ה־SSR helpers של Supabase.

**Backend — Next.js Route Handler**
- מאמת את ה־session האנונימי בכל בקשת יצירה.
- מנרמל ומאמת את הקלט, כולל הגבלת אורך נושא.
- מנסה לשריין שימוש באופן אטומי ב־PostgreSQL, גם במכסת המכשיר וגם בתקרת האתר. מזהה המכשיר ותאריך היום בישראל נקבעים בתוך מסד הנתונים, לא בשרת.
- אם המכסה או התקרה מוצו, מחזיר תשובת מכסה בלי לקרוא ל־OpenAI.
- אם השימוש אושר, קורא ל־OpenAI ומחזיר את הטקסט לממשק.
- אם הקריאה ל־OpenAI נכשלה או חרגה מזמן ההמתנה, משחרר את השריון כך שהניסיון אינו נספר.
- ממיר כשלים של ספק חיצוני לתשובות API צפויות, בלי לחשוף מפתחות, Stack traces או פרטי מערכת.

**Supabase Auth (Anonymous)**
- יוצר משתמשים אנונימיים ומנהל את ה־session שלהם.
- מספק מזהה יציב לכל מכשיר (`auth.uid()`), המשמש כמפתח לנתוני המכסה.
- מגביל את קצב יצירת המשתמשים האנונימיים לפי כתובת IP.

**Supabase PostgreSQL**
- שומר רק את הנתונים הנחוצים לאכיפת המכסה והתקרה.
- מבטיח רשומה אחת לכל מכשיר ולכל יום מקומי, ורשומה אחת לאתר לכל יום.
- אוכף את המכסה והתקרה בעזרת פעולה אטומית ב־Database, כדי שבקשות מקבילות לא יוכלו לאשר יותר מ־10 יצירות למכשיר או 300 לאתר ביום.

**OpenAI API**
- מקבל בקשה מה־Backend בלבד.
- מקבל הוראות ליצור בדיחה קצרה בעברית, בהתאם לנושא או בדיחה כללית אם הנושא ריק.
- ה־API Key נשאר בשרת ואינו נשלח לדפדפן.

## 4. חלוקה ל־Modules ולשכבות לוגיות

מומלץ לארגן את קוד היישום לפי אחריות, בלי ליצור שכבות מופשטות שאינן נחוצות:

1. **UI / Presentation:** מסך יצירת בדיחה, רכיבי טופס, חיווי טעינה והודעות.
2. **Application / Use Cases:** פעולת `Generate Joke` שמנהלת את סדר הפעולות: אימות session, שריון מכסה, קריאה ל־AI והחזרת תוצאה.
3. **Session Module:** יצירה ואימות של Supabase server client, ויצירה אוטומטית של session אנונימי כשאין.
4. **Quota Module:** קריאה לפעולות השריון, האישור, השחרור והצגת המצב ב־Database, ומיפוי מצב מכסה לתשובות API. חישוב היום בישראל מתבצע ב־Database.
5. **AI Provider Module:** בניית הוראות המודל, קריאת OpenAI, אימות התוצאה וטיפול בשגיאות ספק.
6. **Data Access:** גישה לטבלאות ול־Database functions. אין לאפשר ל־Frontend לשנות מוני שימוש ישירות.
7. **Configuration:** טעינת משתני סביבה ואימות קיומם בעת הפעלת סביבת השרת.

יש להפריד בין קוד שרץ בדפדפן לבין קוד שרץ בשרת. כל מודול שמשתמש ב־OpenAI secret או בהרשאות Database מוגברות חייב להיות Server-only.

## 5. Data Model

### 5.1 טבלת `daily_usage`

מונה השימוש היומי של כל מכשיר (משתמש אנונימי).

| שדה | סוג מוצע | תפקיד |
|---|---|---|
| `user_id` | `uuid` | המזהה האנונימי של המכשיר מ־Supabase Auth (`ON DELETE CASCADE`) |
| `usage_date` | `date` | התאריך הקלנדרי לפי `Asia/Jerusalem` |
| `count` | `integer` | מספר היצירות שנספרות באותו יום: שריונים שעדיין בטיפול ויצירות שהצליחו |
| `updated_at` | `timestamptz` | מועד עדכון אחרון |

**אילוצים ואינדקסים**
- מפתח ראשי מורכב או אילוץ `UNIQUE (user_id, usage_date)` כדי למנוע רשומות כפולות.
- `count` חייב להיות מספר שלם בטווח 0–10.
- אין צורך בטבלת בדיחות: לפי ה־PRD, לא נשמרת היסטוריה והבדיחה הקודמת מוחלפת בממשק.

### 5.1א טבלת `site_daily_usage`

מונה יומי אחד לכל האתר, לתקרה של 300 (PRD 4.א.4).

| שדה | סוג מוצע | תפקיד |
|---|---|---|
| `usage_date` | `date` | מפתח ראשי; התאריך לפי `Asia/Jerusalem` |
| `count` | `integer` | בטווח 0–300; שריונים בטיפול ויצירות שהצליחו, מכל המכשירים |
| `updated_at` | `timestamptz` | מועד עדכון אחרון |

- הטבלה אינה נגישה ללקוח (RLS ללא policies); הגישה רק דרך הפונקציות בסעיף 5.2.

### 5.1ב טבלת `generation_reservations`

שריון אחד לכל לחיצה על יצירת בדיחה. נדרשת כדי שניסיון שנכשל לא ייספר (PRD 4.א.4), בלי לאפשר למשתמש "להחזיר" לעצמו מכסה כרצונו.

| שדה | סוג מוצע | תפקיד |
|---|---|---|
| `id` | `uuid` | מזהה אקראי של השריון; נשאר בשרת ואינו נשלח לדפדפן |
| `user_id` | `uuid` | המזהה האנונימי של המכשיר (`ON DELETE CASCADE`) |
| `usage_date` | `date` | היום בישראל שבו נעשה השריון |
| `status` | `text` | `pending` / `succeeded` / `released` |
| `created_at` | `timestamptz` | מועד השריון |

- הטבלה אינה נגישה ללקוח לקריאה או לכתיבה (RLS ללא policies לתפקיד `authenticated`); הגישה רק דרך הפונקציות בסעיף 5.2.
- אין בה נושא או טקסט בדיחה.

### 5.2 אכיפה אטומית של המכסה והתקרה

ארבע PostgreSQL functions, כל אחת בטרנזקציה אחת. הן מוגדרות `SECURITY DEFINER` עם `search_path` קבוע, והרשאת `EXECUTE` ניתנת רק לתפקיד `authenticated` (משתמשים אנונימיים של Supabase מקבלים תפקיד זה). השרת מפעיל אותן בשם המשתמש האנונימי (עם ה־JWT שלו), ולכן **אין צורך במפתח השרת הסודי של Supabase**.

**`reserve_joke_generation()` — ללא פרמטרים**
1. מזהה את המכשיר לפי `auth.uid()`; אם אין session — נכשלת.
2. מחשבת את היום בישראל בתוך מסד הנתונים: `(now() AT TIME ZONE 'Asia/Jerusalem')::date`.
3. בטרנזקציה אחת: מגדילה את `daily_usage.count` של המכשיר רק אם הוא קטן מ־10, ואת `site_daily_usage.count` רק אם הוא קטן מ־300 (`INSERT ... ON CONFLICT ... DO UPDATE ... WHERE count < N` או מנגנון אטומי שקול). אם אחת משתי ההגדלות לא אושרה — אף אחת מהן לא נשמרת.
4. אם אושר — יוצרת רשומת `generation_reservations` במצב `pending` ומחזירה את מזהה השריון ואת מספר היצירות שנותרו למכשיר. אחרת — מחזירה תוצאה חד־משמעית: `DEVICE_LIMIT` או `SITE_LIMIT`, בלי ליצור שריון.

**`complete_joke_generation(reservation_id)`**
- מסמנת שריון `pending` של המכשיר המחובר כ־`succeeded`. אינה משנה מונים.

**`release_joke_generation(reservation_id)`**
- רק עבור שריון `pending` של המכשיר המחובר: מסמנת אותו `released` ומקטינה ב־1 גם את `daily_usage.count` וגם את `site_daily_usage.count` של ה־`usage_date` של השריון (לא של היום הנוכחי, למקרה שהשחרור קורה אחרי חצות).
- שריון שכבר `succeeded` או `released` אינו משתנה, כך שאי אפשר להחזיר מכסה פעמיים.

**`get_quota_status()` — ללא פרמטרים, קריאה בלבד**
- מחזירה כמה בדיחות נותרו למכשיר היום, והאם התקרה של האתר מוצתה. משמשת להצגת „נשארו X מתוך 10” ולהחלטה אם להציג את מסך המכסה כבר בפתיחה.

**מדוע זה בטוח:** המשתמש אינו יכול לבחור תאריך או מכשיר אחר, כי שניהם נקבעים במסד הנתונים. מזהה השריון אינו נשלח לדפדפן והטבלה אינה קריאה ללקוח, ולכן המשתמש אינו יכול לשחרר שריון של בדיחה שקיבל. אם יפעיל את `reserve` ישירות, הוא רק יצרוך את המכסה של עצמו ואת התקרה של האתר, בלי לקבל בדיחה.

אין לבצע `SELECT count` ואז `UPDATE count` בשתי בקשות נפרדות, כי בקשות מקבילות עלולות לעקוף את המכסה.

### 5.3 מועד איפוס המכסה

- אזור הזמן העסקי הוא `Asia/Jerusalem`, ולא UTC.
- תאריך המכסה נקבע **רק בתוך PostgreSQL** (סעיף 5.2), עם הערך הקבוע `Asia/Jerusalem`. השרת אינו מחשב ואינו מעביר תאריך.
- אין לחשב את היום לפי שעון המכשיר של המשתמש.
- שימוש בסוג `date` עבור `usage_date` מפשט את המעבר בין שעון קיץ לשעון חורף: המכסה והתקרה מתחדשות כשהתאריך המקומי בישראל מתחלף בחצות.
- בדיקות חייבות לכלול את רגע חצות ואת המעברים בין שעון קיץ לשעון חורף.

### 5.4 מדיניות ניסיון חוזר

לפי ה־PRD (4.א.4), רק בדיחה שהתקבלה בהצלחה נספרת. המימוש הוא שריון ושחרור (סעיף 5.2):

- לפני הקריאה ל־OpenAI — `reserve`. המקום נתפס מיד, כך שבקשות מקבילות אינן יכולות לחרוג מ־10 למכשיר או מ־300 לאתר.
- הבדיחה התקבלה ועברה אימות — `complete`. הבדיחה נספרת גם אם לא הגיעה למכשיר בגלל ניתוק אחרי היצירה.
- OpenAI נכשל, החזיר תוצאה לא תקינה או חרג מזמן ההמתנה (סעיף 6.3) — `release`, והניסיון אינו נספר.
- אם השרת קרס בין `reserve` לבין `complete`/`release`, השריון נשאר `pending` ונספר. זו פשרה מכוונת: מקרה נדיר, ולא מתבצע ניקוי אוטומטי בגרסה הראשונה.

## 6. API וזרימת מידע

### 6.1 `POST /api/jokes`

**דרישה:** session אנונימי תקף (נוצר אוטומטית, סעיף 7.1).

**בקשת JSON**
```json
{
  "topic": "חתולים"
}
```

`topic` יכול להיות מחרוזת ריקה או חסר, ובמקרה כזה נוצרת בדיחה כללית. יש לבצע `trim`, להגביל את האורך ל־100 תווים (PRD 4.א.2) ולדחות טיפוסים לא תקינים.

**תגובה מוצלחת — HTTP 200**
```json
{
  "joke": "טקסט הבדיחה בעברית",
  "remainingToday": 7
}
```

**תגובות צפויות**
- `400 Bad Request` — קלט לא תקין או נושא ארוך מהמותר.
- `401 Unauthorized` — אין session תקף. ה־Frontend מרענן את הדף (ה־Proxy יוצר session חדש) ומאפשר לנסות שוב; אין מסך התחברות.
- `429 Too Many Requests` — המכסה מוצתה; התגובה כוללת קוד יציב: `DAILY_LIMIT_REACHED` (מכשיר) או `SITE_LIMIT_REACHED` (אתר). שניהם מוצגים באותו מסך מכסה.
- `502 Bad Gateway` — ספק ה־AI נכשל או החזיר תוצאה שאינה תקינה. השריון משוחרר.
- `504 Gateway Timeout` — ספק ה־AI לא ענה בזמן (סעיף 6.3). השריון משוחרר.
- `503 Service Unavailable` — שירות נדרש אינו זמין זמנית.
- `500 Internal Server Error` — תקלה בלתי צפויה, ללא פרטים פנימיים בתגובה.

נוסח ההודעות שמוצגות למשתמש יישאר בעברית, בהתאם ל־PRD. ה־API יחזיר קודי שגיאה יציבים כדי שה־Frontend יוכל להציג הודעות מתאימות בלי להסתמך על טקסט טכני.

### 6.2 זרימת יצירת בדיחה

1. המשתמש שולח נושא או שדה ריק מה־Frontend.
2. ה־Backend מאמת את ה־session האנונימי בצד השרת.
3. ה־Backend מנרמל את הנושא ובודק את תקינותו.
4. השרת קורא ל־`reserve_joke_generation()` בשם המשתמש האנונימי. מסד הנתונים קובע את המכשיר ואת היום בישראל, ובודק גם את תקרת האתר.
5. אם המכסה או התקרה מוצו, מוחזרת שגיאת מכסה; לא מתבצעת קריאה ל־OpenAI.
6. אם השימוש אושר, השרת שולח ל־OpenAI הוראות בעברית ונושא הבדיחה. מפתח ה־API נשלף ממשתנה סביבה בצד השרת.
7. השרת מאמת שהתקבלה תוצאה טקסטואלית תקינה, קורא ל־`complete_joke_generation` ומחזיר את הבדיחה ללקוח.
8. אם OpenAI נכשל, החזיר תוצאה לא תקינה או חרג מזמן ההמתנה, השרת קורא ל־`release_joke_generation` ומחזיר שגיאה.
9. ה־Frontend מסיר את חיווי הטעינה ומחליף את הבדיחה המוצגת בתוצאה החדשה.
10. במקרה של כשל, או אם לא התקבלה תשובה תוך 25 שניות, ה־Frontend מציג הודעת שגיאה ואפשרות מפורשת לנסות שוב. הניסיון החדש עובר שוב את בדיקת המכסה.

### 6.3 קריאה ל־OpenAI

- להשתמש ב־OpenAI SDK הרשמי ל־JavaScript/TypeScript וב־API המתועד העדכני.
- לבצע את הקריאה רק ב־Route Handler בצד השרת.
- להשתמש במזהה המודל שאושר עבור דרישת GPT-5. לשמור אותו במשתנה סביבה, למשל `OPENAI_MODEL`, כדי שלא לקבע מזהה ישן בקוד; ערך ברירת המחדל בפריסה חייב להיות מזהה GPT-5 מאומת וזמין.
- GPT-5 הוא מודל "חושב", ושלב החשיבה נספר בתוך `max_output_tokens`. לכן יש לבקש רמת חשיבה מינימלית (`reasoning.effort` הנמוך ביותר שהמודל תומך בו), ולהגדיר `max_output_tokens` שמשאיר מקום גם לבדיחה עצמה. תשובה ריקה או קטועה נחשבת כשל (`502`) ומשחררת את השריון.
- **זמני המתנה:** הלקוח מחכה עד 25 שניות (PRD 4.א.5). הקריאה ל־OpenAI בשרת מוגבלת לכ־20 שניות, כדי שהשרת יספיק לשחרר את השריון ולהחזיר `504` לפני שהלקוח מוותר. מגבלת זמן הריצה של הפונקציה ב־Vercel (`maxDuration`) תוגדר כ־30 שניות לפחות.
- לטפל בשגיאות רשת, rate limits ושגיאות ספק.
- הוראות המודל צריכות לקבוע שהפלט יהיה בדיחה בעברית, קשורה לנושא אם הוזן, וכללית אם לא הוזן; באורך של עד 4 שורות; נקייה ולא פוגענית, ובנושא רגיש בדיחה עדינה בנושא קרוב במקום סירוב (PRD 4.א.3).
- הנושא מועבר למודל כנתון בלבד, מופרד מההוראות (למשל בהודעת משתמש נפרדת ובין מפרידים), והוראות המערכת קובעות שתוכן הנושא אינו הוראה.
- **מזהה המודל:** GPT-5 הראשי בלבד. בדיקת ההגדרות דוחה מזהה שאינו מתחיל ב־`gpt-5` או שהוא גרסה מוקטנת (`mini`/`nano`).
- **אימות התשובה:** תשובה ריקה, תשובה בלי אותיות עבריות או תשובה ארוכה במיוחד (מעבר לכ־600 תווים) נחשבות כשל (`502`), והשריון משתחרר.
- אין להחזיר למשתמש מידע אבחוני של ספק ה־AI, ואין להפעיל ניסיון חוזר אוטומטי בלתי מוגבל.

## 7. זיהוי מכשיר, הרשאות ואבטחה

### 7.1 Session אנונימי

- **אין התחברות** ואין מסך התחברות (PRD 4.א.1). כל מכשיר מקבל משתמש אנונימי של Supabase Auth (Anonymous Sign-Ins) באופן אוטומטי.
- את האפשרות **Allow anonymous sign-ins** יש להפעיל בהגדרות Auth של כל פרויקט Supabase (Development ו־Production). זו הגדרה שאינה עוברת ב־Migrations (סעיף 9.4).
- ה־Proxy/Middleware של Next.js יוצר session אנונימי כשאין, ומרענן session שפג, באמצעות Supabase SSR helpers ו־cookies מאובטחים (`HttpOnly`, `Secure`, `SameSite=Lax`).
- ה־Backend חייב לאמת session בכל בקשת יצירה. אין להסתמך על מזהה שמגיע בגוף הבקשה.
- לא נאסף ולא נשמר שום פרט אישי (שם, אימייל, תמונה).

### 7.2 הרשאות Database

- להפעיל Row Level Security (RLS) על `daily_usage`, `site_daily_usage` ו־`generation_reservations`.
- אין לתת ללקוח הרשאת `INSERT`, `UPDATE` או `DELETE` על נתוני המכסה, ואין policies ללקוח על `site_daily_usage` ו־`generation_reservations`. מותר policy של `SELECT` על `daily_usage` לשורות של המכשיר עצמו בלבד (`user_id = auth.uid()`).
- שינוי נתוני המכסה מתבצע רק דרך הפונקציות בסעיף 5.2. הן מזהות את המכשיר לפי `auth.uid()` ואינן מקבלות מזהה או תאריך מבחוץ.
- לא נעשה שימוש ב־`service_role` או במפתח שרת סודי של Supabase לצורך המכסה.

### 7.3 ניהול סודות

- `OPENAI_API_KEY` נשמר רק ב־Environment Variables של סביבת השרת. האפליקציה אינה צריכה מפתח שרת סודי של Supabase (סעיף 7.2).
- ערכים בעלי קידומת `NEXT_PUBLIC_` נחשבים ציבוריים ואסור להציב בהם סודות.
- `.env` משמש לפיתוח בלבד, מחוץ ל־Git (ADR-1); יש לכלול `.env*` ב־`.gitignore` ולהוסיף `.env.example` עם שמות משתנים ללא ערכים.
- אין להדפיס סודות או תוכן רגיש ל־logs.

### 7.4 הגנות נוספות

- לאכוף מכסה ותקרה ב־Database ולא ב־Frontend בלבד.
- להגביל אורך נושא ל־100 תווים ולוודא ש־`topic` הוא מחרוזת.
- להחזיר הודעות שגיאה כלליות ללקוח ולשמור פרטים טכניים רק ב־server logs.
- להשתמש ב־HTTPS, cookies מאובטחים, בדיקת `Origin`/CSRF בהתאם לדפוס ה־session, והגדרות CORS מצומצמות אם נדרשות.
- להשאיר מופעלת את מגבלת הקצב של Supabase על יצירת משתמשים אנונימיים לפי IP. לא להוסיף rate limiting נפרד או CAPTCHA בגרסה הראשונה; התקרה הכללית של האתר מגבילה את העלות. אפשר להוסיף הגנה בהמשך בלי לשנות את מודל הנתונים.
- לא לשמור נושאים או בדיחות ב־logs כברירת מחדל. אין ב־PRD דרישת היסטוריה או מדיניות שמירת תוכן.

## 8. PWA, ממשק ו־Offline

- להגדיר Web App Manifest באמצעות מנגנון `manifest` של Next.js, כולל `name`, `short_name`, `start_url`, `display: "standalone"`, צבעי theme ו־icons בגודל הנדרש.
- לוודא שהאתר מוגש ב־HTTPS ושקובצי האייקונים זמינים.
- יש לבדוק התקנה בדפדפנים ניידים תומכים. אפשרויות ההתקנה משתנות בין iOS, Android ודפדפנים. האתר המותקן מקבל session אנונימי משלו, ולכן ייתכן שתהיה לו מכסה נפרדת מזו של הדפדפן באותו טלפון; זה תקין.
- Service Worker יתווסף רק אם נדרש לצורך התקנה/עדכון או caching בסיסי; אין לממש יצירת בדיחות Offline.
- אין לשמור בדיחות קודמות ב־local storage או ב־IndexedDB. ניתן להשאיר בזיכרון הממשק את הבדיחה הנוכחית בלבד.
- יש להגדיר `lang="he"` ו־`dir="rtl"`, ולוודא שהודעות טעינה, שגיאה ומכסה בעברית.

## 9. Environments, GitHub ו־Deployment

### 9.1 סביבות נפרדות

יש להשתמש בשני פרויקטים נפרדים ב־Supabase:

1. **Development:** משמש לפיתוח ולבדיקות. סביבת הפיתוח המקומית מחוברת לפרויקט זה בלבד.
2. **Production:** מכיל את נתוני השימוש של האתר החי. פרטי הגישה אליו נשמרים רק ב־Vercel ובמערכת הפריסה המאובטחת; אין להורידם לסביבת הפיתוח המקומית.

גם ב־Vercel יש להגדיר משתני Environment לפי סביבה. סודות Production יהיו מוגדרים רק עבור Production. ערכי Development ו־Preview של Vercel, אם נדרשים, יפנו לפרויקט Supabase Development ולא ל־Production.

**משתנים**
- `NEXT_PUBLIC_SUPABASE_URL` — כתובת הפרויקט המתאים לסביבה.
- `NEXT_PUBLIC_SUPABASE_ANON_KEY` — מפתח לקוח ציבורי (anon או publishable) לפי תצורת Supabase.
- `OPENAI_API_KEY` — סוד OpenAI בצד השרת.
- `OPENAI_MODEL` — מזהה מודל GPT-5 שאושר.

אזור הזמן העסקי (`Asia/Jerusalem`) והמספרים 10 ו־300 אינם משתני סביבה: הם כללים קבועים של המוצר ומוגדרים בתוך מסד הנתונים (סעיף 5.2).

אין לשמור את מפתחות Production בקובץ מקומי, ב־GitHub או ב־`.env` של הפיתוח. כתובות ומפתחות ציבוריים אינם תחליף להגדרת RLS והרשאות.

### 9.2 Git ו־Build

- כל קוד המקור וקובצי `supabase/migrations/` נשמרים ב־Git Repository ב־GitHub.
- חיבור ה־Repository ל־Vercel מאפשר Preview Deployment לענפים/בקשות מיזוג ו־Production Deployment מהענף הראשי, לפי הגדרות הפרויקט. החיבור מתבצע ב־M5 (ADR-6 הוחלף ב־ADR-9).
- כל שינוי קוד עובר Build ובדיקות אוטומטיות. אין לפרוס גרסה אם ה־Build נכשל.
- משתני סביבה מוגדרים ב־Vercel לפי הסביבה ואינם נשמרים ב־Repository.
- יש להגדיר בדיקות בסיסיות עבור session אנונימי, מכסה, תקרה, יצירה, שגיאות ו־RTL. בדיקות יחידה משתמשות ב־session ובתשובות OpenAI מדומים.
- **בדיקות E2E (Playwright):** אין התחברות, ולכן Playwright בודק את הזרימה המלאה מול סביבת Development. כדי לצמצם עלות, הבדיקות שקוראות ל־OpenAI האמיתי מוגבלות למספר קטן של בדיחות בכל הרצה, ובדיקות המכסה והשגיאות נעשות בבדיקות יחידה עם תשובות מדומות.

### 9.3 Database Migrations — נוהל מחייב

שינויים בסכימת Database ינוהלו באמצעות קובצי SQL ב־`supabase/migrations/`, הנשמרים ב־GitHub.

1. יוצרים Migration file ומתעדים בו שינוי סכימה בלבד, או שינוי Database נוסף שניתן לשחזר באופן מבוקר.
2. מריצים ובודקים את ה־Migration מול פרויקט Supabase **Development בענן**. אין דרישה מהמשתמש להתקין Docker או להריץ Supabase מקומי.
3. בודקים את האפליקציה מול Development: session אנונימי, יצירה, מכסה, תקרה, מקרי קצה ותאימות הקוד לסכימה.
4. לאחר שהבדיקות עברו, מציגים למשתמש את השינוי ומבקשים אישור מפורש לפני שינוי Production.
5. לאחר אישור, **המשתמש מפעיל בלחיצה** GitHub Actions workflow ייעודי (`workflow_dispatch`, למשל `.github/workflows/migrate-production.yml`), שמריץ `supabase db push` מול פרויקט Production. ה־workflow אינו רץ אוטומטית על push. פרטי הגישה ל־Production (`SUPABASE_ACCESS_TOKEN`, מזהה הפרויקט וסיסמת מסד הנתונים) נשמרים רק כ־GitHub Secrets, והמשתמש מזין אותם בעצמו; הם לעולם אינם נמצאים במחשב המקומי.
6. רק לאחר שה־Migration ב־Production הושלם בהצלחה, מתבצע Production Deployment של גרסת האפליקציה שתלויה בסכימה החדשה.
7. אם ה־Migration נכשל, עוצרים את פריסת האפליקציה ומטפלים בכשל לפני ניסיון נוסף.
8. אין לבצע שינויי סכימה ידניים ב־Production דרך Dashboard/SQL Editor לאחר שהתחיל שימוש ב־migrations. במקרה חירום, יש לתעד ולסנכרן את השינוי עם היסטוריית ה־migrations לפני המשך עבודה.

כלי הפיתוח/AI מכין את ה־workflow ומדריך את המשתמש, אך לעולם אינו משתמש בפרטי Production מהמחשב המקומי. תהליך ה־Deployment חייב להיות מסודר כך שעדכון מסד הנתונים קודם לגרסת האפליקציה שדורשת אותו.

### 9.4 הגדרות שאינן עוברות ב־Database Migrations

יש להגדיר ולבדוק בנפרד בכל אחד משני פרויקטי Supabase:

- **Allow anonymous sign-ins** בהגדרות Auth (סעיף 7.1), ומגבלת הקצב ליצירת משתמשים אנונימיים.
- כתובות אתר ו־Site URL של Auth.
- סודות ו־API keys.
- הגדרות פרויקט, הרשאות משתמשים, ותפקידי גישה.
- הגדרות שירותי Supabase שאינן מוגדרות במפורש כקוד או כ־config בפרויקט.
- הגדרות Billing, Limits ו־Compute.
- משתני Environment ב־Vercel.
- GitHub Secrets של ה־workflow להרצת Migrations ב־Production (סעיף 9.3).

אפשר לנהל חלק מהגדרות Supabase באמצעות קובצי config או CI, אך אין להניח ש־SQL migrations מעבירות סודות או הגדרות ספק חיצוני. יש לוודא בפועל שכל סביבה מוגדרת כראוי.

### 9.5 עלויות ומגבלות תוכניות

- **Supabase Free:** לפי תיעוד Supabase העדכני, התוכנית כוללת שני פרויקטים חינמיים פעילים לכלל הארגונים שבהם המשתמש Owner/Admin. פרויקטים Free עם פעילות נמוכה עשויים להיות מושהים אוטומטית לאחר כשבעה ימים; החזרה לפעילות עשויה לדרוש הפעלה מחדש. לכן שני פרויקטים אפשריים לפיתוח ראשוני, אך יש לתכנן תוכנית בתשלום עבור Production שדורש זמינות רציפה.
- **החלטה (PRD 5.ב):** בשלב זה שימוש אישי ולא מסחרי, בתוכניות החינמיות. כדי שפרויקט Production לא יושהה לפני שמשתמשים בו, הוא **נוצר רק ב־M5**. לפני העלייה לאוויר בעל המוצר מחליט אם לעבור לתוכנית בתשלום.
- **Supabase בתשלום:** לכל פרויקט יש משאבי Compute ועלות משלו, בנוסף לתוכנית הארגון ולשימוש משתנה. יש לבדוק את המחיר העדכני לפני בחירת התוכנית.
- **Vercel Hobby:** התוכנית החינמית מיועדת לשימוש אישי ולא מסחרי. אם המוצר מופעל כשירות מסחרי או עסקי, יש לבחור תוכנית שמתירה שימוש זה, בדרך כלל Pro.
- **OpenAI API:** העלות תלויה במודל ובכמות ה־input/output tokens. בדיחה קצרה צפויה להשתמש במעט tokens, והתקרה של 300 בדיחות ביום מגבילה את העלות היומית. בנוסף יש להגדיר תקציב והתראות ולוודא את התמחור המדויק של מזהה המודל שנבחר.

## 10. Configuration, Observability וטיפול בתקלות

- בעת עליית השרת יש לוודא שמשתני הסביבה הנדרשים קיימים; אם חסר סוד חובה, יש להיכשל בצורה ברורה ב־startup ולא לחשוף ערכים.

- אין להציג למשתמש שגיאות פנימיות. כל הודעות ה־UI בעברית.
- יש להגדיר התראות שימוש/חיוב ב־OpenAI ובשירותי Hosting/Database לפי האפשרויות הזמינות בתוכנית.
- במקרה של אובדן חיבור לאינטרנט, הממשק מציג הודעה ואפשרות לנסות שוב לאחר חזרת החיבור. אין להציג תוצאה ישנה כאילו נוצרה כעת.

## 11. בדיקות וקריטריוני תקינות ארכיטקטוניים

יש לכסות לפחות את המקרים הבאים:

- כשל OpenAI או ניתוק רשת מציג הודעה בעברית ואפשרות מפורשת לנסות שוב.
- מפתחות OpenAI וסודות שרת אינם נחשפים בקוד לקוח, בקובצי Git או בתגובות API.
- סביבת Development אינה קוראת או כותבת ל־Database של Production.
- Migration נבדק ב־Development ומאושר לפני הרצה ב־Production; פריסת קוד שתלויה בשינוי סכימה אינה מקדימה את ה־Migration.

## החלטות מרכזיות (ADRs)

### ADR-1: קובץ סביבה מקומי `.env` במקום `.env.local`
**הקשר:** המסמכים מזכירים `.env.local`, אך הנחיות העבודה בפרויקט (CLAUDE.md) קובעות שהקובץ המקומי הוא `.env`, המועתק פעם אחת מ-`.env.example`.
**החלטה:** הפיתוח המקומי משתמש ב-`.env`, ובו פרטי Supabase Development בלבד. Next.js טוען אותו באותו אופן.
**השלכות:** `.gitignore` חוסם את `.env` ואת `.env.*` (כולל `.env.local`). משתנה חדש מתווסף קודם ל-`.env.example`, ואז מבקשים מהמשתמש להוסיף אותו ל-`.env`.

### ADR-2: Manifest דרך `app/manifest.ts`, בלי Service Worker
**הקשר:** נדרש Manifest של PWA. ARCHITECTURE §8 מורה להשתמש במנגנון ה-manifest של Next.js, ולהוסיף Service Worker רק אם הוא נדרש בפועל.
**החלטה:** הקובץ `app/manifest.ts` מוגש בכתובת `/manifest.webmanifest`. האייקונים נמצאים ב-`public/icons/` ונוצרים מ-`icon.svg` באמצעות `scripts/generate-icons.mjs`. בשלב זה אין Service Worker.
**השלכות:** Chrome מזהה את ה-Manifest ומאפשר התקנה. אם בדיקת ההתקנה במכשירים אמיתיים ב-M5 תדרוש Service Worker, הוא יתווסף אז.

### ADR-3: בדיקות הגדרות בעליית השרת (`instrumentation.ts`)
**הקשר:** ARCHITECTURE §10 דורש כשל ברור בעלייה כשחסר סוד חובה. M1 דורש בנוסף לוודא שמודל GPT-5 שב-`OPENAI_MODEL` זמין.
**החלטה:** הפונקציה `register()` מריצה פעם אחת את `runStartupChecks()` (`lib/config/`). הבדיקה מוודאת שכל משתני החובה קיימים, ושהמודל הוא GPT-5 הראשי (מתחיל ב-`gpt-5`, לא `mini`/`nano`).
- **בפיתוח בלבד** נבדקים גם זמינות המודל (`models.retrieve`, לא צורך tokens) והחיבור ל-Supabase (`/auth/v1/health`). מפתח שנדחה או מודל שאינו קיים עוצרים את השרת. תקלה זמנית (אין רשת, עומס, שגיאת שרת של הספק) מציגה אזהרה בלבד.
- **ב-Production** (`NODE_ENV=production`) לא מתבצעות פניות לשירותים חיצוניים בעלייה, כדי ש-cold start ב-Vercel לא יאט ולא יפיל את האתר בגלל תקלה זמנית אצל ספק. נבדקים רק משתני החובה ומזהה המודל.
**השלכות:** הבדיקות לא רצות ב-`next build`, ולכן ה-build לא תלוי בסודות. הודעות השגיאה כוללות רק שמות של משתנים, לא ערכים. לא מוחלף מודל אוטומטית. מודל שאינו זמין ב-Production יתגלה בקריאה הראשונה, כשגיאת `502` שמשחררת את השריון.

### ADR-4: שריון ושחרור מכסה, ללא מפתח שרת של Supabase
**הקשר:** ה־PRD קובע שרק בדיחה שהתקבלה בהצלחה נספרת. בנוסף, בתכנון הקודם השרת העביר למסד הנתונים מזהה משתמש ותאריך, ומשתמש שמפעיל את הפונקציה ישירות היה יכול לבחור תאריך אחר ולקבל מכסה בלי הגבלה.
**החלטה:** פונקציות `reserve`, `complete`, `release` (ו־`get_quota_status` לקריאה) בלי פרמטרים של משתמש או תאריך. המכשיר נקבע לפי `auth.uid()` והיום לפי `Asia/Jerusalem` בתוך PostgreSQL. טבלת `generation_reservations` מאפשרת לשחרר רק שריון `pending`, ומזהה השריון נשאר בשרת. הפונקציות מופעלות בשם המשתמש האנונימי של המכשיר (ADR-9).
**השלכות:** אין צורך ב־`SUPABASE_SERVICE_ROLE_KEY`. שריון שנשאר `pending` בגלל קריסת שרת נספר (מקרה נדיר, ללא ניקוי אוטומטי).

### ADR-5: הרצת Migrations ב־Production דרך GitHub Actions בהפעלה ידנית
**הקשר:** אסור להשתמש בפרטי Production מהמחשב המקומי, ולא הוגדרה דרך מותרת אחרת להריץ Migrations על Production.
**החלטה:** workflow של GitHub Actions שמופעל רק בלחיצה (`workflow_dispatch`) ומריץ `supabase db push` מול Production. הסודות נשמרים ב־GitHub Secrets, והמשתמש מזין אותם בעצמו.
**השלכות:** המשתמש מפעיל את ההרצה בעצמו מתוך GitHub, אחרי אישור. ה־workflow מוכן ונבדק לפני הפריסה ב־M5.

### ADR-6: חיבור Vercel כבר ב־M2 — **הוחלף ב־ADR-9**
**הקשר:** החיבור המוקדם ל־Vercel נדרש כדי לבדוק התחברות Google מתוך אתר מותקן בטלפון.
**החלטה:** בטלה. אין יותר התחברות Google, ולכן אין צורך בבדיקה המוקדמת. Vercel מחובר ב־M5.
**השלכות:** M2 אינו דורש push ל־GitHub או חיבור Vercel.

### ADR-7: כיבוי הגדרות ניסיוניות של Next.js
**הקשר:** תבנית `create-next-app` הפעילה ב-`next.config.ts` את `cacheComponents` ואת `partialPrefetching`. אלה משנות את אופן השמירה במטמון של דפים, ועלולות להסתבך עם דפים שתלויים ב-session ב-cookies (M2).
**החלטה:** שתי ההגדרות כבויות. הדפים מתנהגים לפי ברירת המחדל של App Router.
**השלכות:** התנהגות צפויה ופשוטה יותר עם ה־session האנונימי. אם יידרש שיפור ביצועים, אפשר לשקול להפעיל אותן מחדש בהחלטה נפרדת.

### ADR-8: אזור הזמן כקבוע ולא כמשתנה סביבה
**הקשר:** `APP_TIME_ZONE` הוגדר כמשתנה סביבה, אבל שעון ישראל הוא כלל קבוע של המוצר, ותאריך המכסה מחושב רק במסד הנתונים (ADR-4). הגדרה שגויה בסביבה אחת הייתה שוברת את המכסה בשקט.
**החלטה:** `APP_TIME_ZONE` הוסר מ-`.env.example` ומהקוד. הערך `Asia/Jerusalem` קבוע בפונקציות של מסד הנתונים, ובקוד (למשל להצגת זמן האיפוס) כקבוע אחד.
**השלכות:** אחד פחות להגדיר בכל סביבה. שינוי אזור הזמן ידרוש שינוי קוד ו-Migration, כמו כל שינוי בכלל עסקי.

### ADR-9: בלי התחברות — Supabase Anonymous Sign-Ins ותקרה כללית לאתר
**הקשר:** בעל המוצר החליט לוותר על התחברות Google (PRD 4.א.1). עדיין נדרשת מכסה יומית בצד השרת, ונדרשת הגנה על העלות כשאין זהות אמיתית.
**החלטה:** כל מכשיר מקבל משתמש אנונימי של Supabase Auth, שנוצר אוטומטית ב־Proxy/Middleware ונשמר ב־cookie מאובטח. מנגנון המכסה (ADR-4) נשאר זהה ומשתמש ב־`auth.uid()` של המשתמש האנונימי. נוספה טבלת `site_daily_usage` עם תקרה של 300 בדיחות ביום לכל האתר, שנאכפת באותה טרנזקציה של מכסת המכשיר. מסכי ההתחברות, שגיאת ההתחברות, הפרופיל והתפריט בוטלו.
**השלכות:** המכסה למכשיר ניתנת לעקיפה (חלון גלישה בסתר, מחיקת cookies), והתקרה הכללית מגבילה את העלות. אם התקרה מוצתה בגלל שימוש לרעה, כל המשתמשים חסומים עד חצות; אם זה יקרה, אפשר להוסיף CAPTCHA בהחלטה נפרדת. יש להפעיל Anonymous Sign-Ins בכל פרויקט Supabase. אין יותר Google OAuth, מסך הסכמה או חיבור Vercel מוקדם (ADR-6).

### ADR-10: cookie של ה־session מסוג HttpOnly, בלי לקוח Supabase בדפדפן
**הקשר:** סעיף 7.1 דורש cookies מאובטחים (`HttpOnly`, `Secure`, `SameSite=Lax`). ברירת המחדל של `@supabase/ssr` היא cookie שאינו HttpOnly, כדי שקוד בדפדפן יוכל להשתמש ב־session.
**החלטה:** כל הפניות ל־Supabase נעשות בשרת (ה־Proxy ב־`proxy.ts`, ובהמשך Server Components ו־`POST /api/jokes`). ה־cookie מוגדר `httpOnly: true` ו־`sameSite: "lax"`, ו־`secure` רק ב־Production, דרך הקבוע `SUPABASE_COOKIE_OPTIONS` ב־`lib/supabase/session.ts`. אין לקוח Supabase בדפדפן. ה־Proxy יוצר משתמש אנונימי חדש רק כשאין session תקף, ולא בתקלה זמנית (שגיאת רשת, שגיאת שרת, או refresh token שכבר נוצל בבקשה מקבילה), כדי שמכשיר לא יקבל מכסה חדשה בגלל תקלה.
**השלכות:** קוד בדפדפן אינו יכול לקרוא את ה־token. כל לקוח Supabase שייווצר בשרת בהמשך חייב להשתמש באותו קבוע. ב־`localhost` ה־cookie אינו `Secure`, כי Safari אינו שומר cookie כזה בכתובת `http`. ה־Proxy קורא את משתני Supabase ישירות מ־`process.env`, כי `lib/config/env.ts` מסומן `server-only`; קיומם נבדק בעליית השרת (ADR-3).
