# ARCHITECTURE.md — ארכיטקטורה טכנית

## 1. מטרת המסמך והנחות יסוד

מסמך זה מתרגם את דרישות `PRD.md` של מערכת ליצירת בדיחות באמצעות AI לתכנון טכני בר־מימוש. המוצר הוא אתר Web בעברית, מותאם למובייל וניתן להתקנה כ־PWA. המשתמש חייב להתחבר באמצעות Google, יכול לבקש בדיחה בעברית בנושא לבחירתו או בדיחה כללית, ומוגבל לעד 10 בקשות יצירה ביום קלנדרי לפי שעון ישראל. בכל רגע מוצגת בדיחה אחת בלבד; אין היסטוריית בדיחות.

ה־PRD קובע שימוש ב־GPT-5, ביצוע קריאות AI בצד השרת בלבד, שמירת מוני השימוש ב־Database ואכיפת המכסה בשרת. הוא אינו מגדיר ספקי תשתית או תקציב. הבחירות להלן הן החלטות ארכיטקטוניות לצורך מימוש פשוט ותחזוקתי, ולא שינוי בדרישות המוצר.

### 2.1 נימוקי הבחירה

- **Next.js + TypeScript + Vercel:** המוצר דורש גם UI וגם נקודת Backend מאובטחת שמפעילה את OpenAI. Next.js מאפשר לרכז אותם באפליקציה אחת, ו־Vercel מתאימה להרצת Next.js ולפריסה אוטומטית מ־GitHub. אין צורך להקים שרת Backend נפרד.
- **Supabase Auth + PostgreSQL:** מספקים OAuth באמצעות Google ומסד נתונים רלציוני מנוהל באותו שירות. PostgreSQL מתאים למונה יומי ייחודי לכל משתמש, לאילוץ `UNIQUE` ולאכיפה אטומית של מכסה גם בבקשות מקבילות.
- **OpenAI API:** נדרש על פי ה־PRD, והקריאה מתבצעת רק ב־Backend. יש לקבע את מזהה המודל לפי ההחלטה המוצרית ולבדוק זמינות ומצב תמיכה לפני העלייה לאוויר.
- **PWA ללא שכבת Offline מורכבת:** דרישת המוצר היא התקנה במכשירים תומכים, לא שימוש מלא ללא חיבור. יצירת בדיחה דורשת רשת ולכן אין לשמור או להציג תוצאה מדומה במצב Offline.
- **ללא Storage, Queue, Analytics או שירותי AI נוספים:** אין ב־PRD העלאת קבצים, היסטוריה, משימות רקע, אנליטיקה או תוכן מדיה. רכיבים כאלה יוסיפו עלות ומורכבות ללא צורך נוכחי.

### 2.2 חלופות שנבחנו בקצרה

- **Frontend/Backend:** React עם Vite ו־Backend נפרד, או Next.js. נבחר Next.js כדי לצמצם שירותים ו־Repositories ולשמור את מפתח OpenAI בצד השרת.
- **Hosting:** GitHub Pages מתאים לאתר סטטי, אך אינו מתאים לבדו לדרישת Backend שמבצע קריאות AI מאובטחות ואוכף מכסה. נבחר Vercel עבור Next.js.
- **Database/Auth:** שירותי Backend מנוהלים אחרים כגון Firebase או Backend ייעודי עם PostgreSQL. נבחר Supabase כדי לקבל PostgreSQL ו־Google OAuth יחד, בלי לתחזק שרת מסד נתונים.
- **PWA:** PWA בסיסית עם Manifest לעומת פתרון Offline מלא. נבחרת האפשרות הבסיסית, משום שיצירת בדיחה תלויה ב־Backend וב־OpenAI.

### 2.3 מגבלות וסיכונים

1. **זמינות GPT-5:** קטלוג המודלים והתיעוד של OpenAI משתנים. נכון למועד המחקר, דפי OpenAI מסמנים חלק ממזהי GPT-5 הישנים או ממשפחת GPT-5 כ־Deprecated ומפרסמים מועדי הסרה למודלים מסוימים. לכן יש לאמת בחשבון ה־API את מזהה המודל המדויק שמותר לשימוש. אין להחליף מודל אוטומטית, משום שה־PRD דורש GPT-5; אם המזהה הנדרש אינו זמין, יש לקבל החלטה מוצרית מפורשת לפני החלפה.
2. **עלויות משתנות:** OpenAI מחייבת לפי מודל ושימוש; Supabase ו־Vercel מגבילים משאבים לפי תוכנית. יש להגדיר התראות שימוש ותקציב ב־OpenAI ולבדוק את התמחור לפני השקה.
3. **תוכנית חינמית של Supabase:** התוכנית החינמית מאפשרת שני פרויקטים פעילים בסך הכול לפי תנאי החשבון/הארגון, אך פרויקטים Free עם פעילות נמוכה עשויים להושהות אוטומטית לאחר כשבוע. לכן היא יכולה להתאים לפיתוח ראשוני, אך אינה בחירה בטוחה ל־Production שצריך להיות זמין באופן רציף.
4. **מגבלות Functions:** יש להגדיר Timeout סביר ל־Backend ולתאם אותו עם זמן התגובה של OpenAI. אין לבצע עיבוד כבד או משימות רקע, שאינם נדרשים למוצר.
5. **OAuth ותצורה:** Google OAuth מחייב הגדרות URL ו־redirect מדויקות בכל סביבה. הגדרות אלה אינן נוצרות אוטומטית מתוך קוד האפליקציה.
6. **שינויי סכימה:** שינויים ב־Database חייבים לעבור דרך Migration files. אין לבצע שינויים ידניים ישירות ב־Production לאחר אימוץ תהליך migrations.

## 3. ארכיטקטורת המערכת

### 3.1 מבט כללי

```text
משתמש במכשיר נייד
        |
        | HTTPS
        v
Next.js PWA (Vercel)
  |                  |
  | Google OAuth     | POST /api/jokes
  v                  v
Supabase Auth     Next.js Route Handler
                     |
                     | אימות session / JWT
                     | בדיקת מכסה אטומית
                     v
                Supabase PostgreSQL
                     |
                     | אם נותרה מכסה
                     v
                OpenAI API (GPT-5)
                     |
                     | טקסט בדיחה בעברית
                     v
             תשובת API לממשק
```

האפליקציה היא **Modular Monolith** קטן: פרויקט Next.js אחד שמכיל את ה־UI ואת ה־Backend endpoints. Supabase מנוהל כשירות חיצוני. אין צורך ב־microservices או בשרת Backend נפרד.

### 3.2 אחריות הרכיבים

**Frontend**
- מציג מסך התחברות ומסך יצירת בדיחה בעברית וב־RTL.
- משתמש ב־Supabase Auth לצורך התחברות באמצעות Google.
- מציג שדה נושא, כפתור יצירה, חיווי טעינה, תוצאה אחת בכל רגע והודעות שגיאה/מכסה.
- שולח בקשות ל־Backend ומציג רק את הבדיחה האחרונה שהתקבלה; אין לשמור היסטוריית בדיחות.
- מונע לחיצות כפולות בממשק לשיפור UX, אך אינו מסתמך על כך כאמצעי אבטחה או אכיפת מכסה.

**Backend — Next.js Route Handler**
- מאמת את session של המשתמש בכל בקשת יצירה.
- מנרמל ומאמת את הקלט, כולל הגבלת אורך נושא.
- מחשב את התאריך המקומי בישראל בצד השרת.
- מנסה לשריין שימוש במסגרת המכסה באופן אטומי ב־PostgreSQL.
- אם המכסה מוצתה, מחזיר תשובת מכסה בלי לקרוא ל־OpenAI.
- אם השימוש אושר, קורא ל־OpenAI ומחזיר את הטקסט לממשק.
- ממיר כשלים של ספק חיצוני לתשובות API צפויות, בלי לחשוף מפתחות, Stack traces או פרטי מערכת.

**Supabase Auth**
- מטפל ב־Google OAuth ובניהול session.
- מספק מזהה משתמש יציב, המשמש כמפתח לקישור נתוני המכסה.
- מפנה חזרה לכתובות Callback שהוגדרו מראש לכל סביבה.

**Supabase PostgreSQL**
- שומר רק את הנתונים הנחוצים לאכיפת המכסה.
- מבטיח רשומה אחת לכל משתמש ולכל יום מקומי.
- אוכף את המכסה בעזרת פעולה אטומית ב־Database, כדי שבקשות מקבילות לא יוכלו לאשר יותר מ־10 יצירות ביום.

**OpenAI API**
- מקבל בקשה מה־Backend בלבד.
- מקבל הוראות ליצור בדיחה קצרה בעברית, בהתאם לנושא או בדיחה כללית אם הנושא ריק.
- ה־API Key נשאר בשרת ואינו נשלח לדפדפן.

## 4. חלוקה ל־Modules ולשכבות לוגיות

מומלץ לארגן את קוד היישום לפי אחריות, בלי ליצור שכבות מופשטות שאינן נחוצות:

1. **UI / Presentation:** מסכי התחברות ויצירת בדיחה, רכיבי טופס, חיווי טעינה והודעות.
2. **Application / Use Cases:** פעולת `Generate Joke` שמנהלת את סדר הפעולות: אימות משתמש, בדיקת/שריון מכסה, קריאה ל־AI והחזרת תוצאה.
3. **Authentication Module:** יצירה ואימות של Supabase server client, בדיקת session וטיפול ב־OAuth callback.
4. **Quota Module:** חישוב היום בישראל, קריאה לפעולה האטומית ב־Database ומיפוי מצב מכסה לתשובות API.
5. **AI Provider Module:** בניית הוראות המודל, קריאת OpenAI, אימות התוצאה וטיפול בשגיאות ספק.
6. **Data Access:** גישה לטבלאות ול־Database function. אין לאפשר ל־Frontend לשנות מוני שימוש ישירות.
7. **Configuration:** טעינת משתני סביבה ואימות קיומם בעת הפעלת סביבת השרת.

יש להפריד בין קוד שרץ בדפדפן לבין קוד שרץ בשרת. כל מודול שמשתמש ב־OpenAI secret או בהרשאות Database מוגברות חייב להיות Server-only.

## 5. Data Model

### 5.1 טבלת `daily_usage`

טבלה אחת מספיקה לגרסה הנוכחית.

| שדה | סוג מוצע | תפקיד |
|---|---|---|
| `user_id` | `uuid` | מזהה המשתמש מ־Supabase Auth; מפתח זר למשתמש המאומת |
| `usage_date` | `date` | התאריך הקלנדרי לפי `Asia/Jerusalem` |
| `count` | `integer` | מספר בקשות היצירה ששוריינו באותו יום |
| `updated_at` | `timestamptz` | מועד עדכון אחרון |

**אילוצים ואינדקסים**
- מפתח ראשי מורכב או אילוץ `UNIQUE (user_id, usage_date)` כדי למנוע רשומות כפולות.
- `count` חייב להיות מספר שלם בטווח 0–10.
- אינדקס לפי `(user_id, usage_date)` אם אינו נוצר כחלק מהמפתח הייחודי.
- אין צורך בטבלת בדיחות: לפי ה־PRD, לא נשמרת היסטוריה והבדיחה הקודמת מוחלפת בממשק.

### 5.2 אכיפה אטומית של המכסה

מומלץ ליצור PostgreSQL function ייעודית, למשל `reserve_joke_generation`, שמבצעת בטרנזקציה אחת את הפעולות הבאות:

1. מקבלת את מזהה המשתמש המאומת ואת תאריך היום בישראל שחושב בשרת.
2. יוצרת רשומת `daily_usage` אם עדיין אין רשומה לאותו משתמש ולאותו יום.
3. מגדילה את `count` רק אם הוא קטן מ־10, תוך שימוש ב־`INSERT ... ON CONFLICT ... DO UPDATE ... WHERE count < 10` או במנגנון אטומי שקול.
4. מחזירה תוצאה חד־משמעית: שימוש אושר או שהמכסה מוצתה.

אין לבצע `SELECT count` ואז `UPDATE count` בשתי בקשות נפרדות, כי בקשות מקבילות עלולות לעקוף את המכסה. יש להפעיל את הפונקציה עם הרשאות מוגבלות ולוודא שהמשתמש אינו יכול להעביר `user_id` שרירותי כדי לצרוך מכסה של חשבון אחר.

### 5.3 מועד איפוס המכסה

- אזור הזמן העסקי הוא `Asia/Jerusalem`, ולא UTC.
- תאריך המכסה נקבע בצד השרת באמצעות ספריית זמן־אזור אמינה או המרה מפורשת ב־PostgreSQL.
- אין לחשב את היום לפי שעון המכשיר של המשתמש.
- שימוש בסוג `date` עבור `usage_date` מפשט את המעבר בין שעון קיץ לשעון חורף: המכסה מתחדשת כשהתאריך המקומי בישראל מתחלף בחצות.
- בדיקות חייבות לכלול את רגע חצות ואת המעברים בין שעון קיץ לשעון חורף.

### 5.4 מדיניות ניסיון חוזר

ה־PRD קובע שניסיון חוזר כפוף למכסה, אך אינו מגדיר אם ניסיון שנכשל מול OpenAI מחזיר את היחידה למכסה. ברירת המחדל הבטוחה למימוש היא לספור כל בקשת יצירה שאושרה ב־Backend, גם אם ספק ה־AI נכשל, כדי למנוע ניצול חוזר ללא גבול ולשמור על כלל פשוט ואטומי. אם המוצר אמור לחייב רק על בדיחות שהוחזרו בהצלחה, יש להגדיר מדיניות זו במפורש ולממש מנגנון reservation/refund אטומי עם טיפול במקרי timeout; אין לבצע החזר אוטומטי חלקי ולא עקבי.

## 6. API וזרימת מידע

### 6.1 `POST /api/jokes`

**דרישה:** משתמש מחובר בלבד.

**בקשת JSON**
```json
{
  "topic": "חתולים"
}
```

`topic` יכול להיות מחרוזת ריקה או חסר, ובמקרה כזה נוצרת בדיחה כללית. יש לבצע `trim`, להגביל אורך קלט ולדחות טיפוסים לא תקינים.

**תגובה מוצלחת — HTTP 200**
```json
{
  "joke": "טקסט הבדיחה בעברית",
  "remainingToday": 7
}
```

**תגובות צפויות**
- `400 Bad Request` — קלט לא תקין או נושא ארוך מהמותר.
- `401 Unauthorized` — המשתמש אינו מחובר או שה־session אינו תקף.
- `429 Too Many Requests` — המכסה היומית מוצתה; התגובה כוללת קוד שגיאה יציב, למשל `DAILY_LIMIT_REACHED`, ומספר המכסה/זמן האיפוס לפי הצורך.
- `502 Bad Gateway` — ספק ה־AI נכשל או החזיר תוצאה שאינה תקינה.
- `503 Service Unavailable` — שירות נדרש אינו זמין זמנית.
- `500 Internal Server Error` — תקלה בלתי צפויה, ללא פרטים פנימיים בתגובה.

נוסח ההודעות שמוצגות למשתמש יישאר בעברית, בהתאם ל־PRD. ה־API יחזיר קודי שגיאה יציבים כדי שה־Frontend יוכל להציג הודעות מתאימות בלי להסתמך על טקסט טכני.

### 6.2 זרימת יצירת בדיחה

1. המשתמש שולח נושא או שדה ריק מה־Frontend.
2. ה־Backend מאמת את ה־session בצד השרת.
3. ה־Backend מנרמל את הנושא ובודק את תקינותו.
4. השרת מחשב את `usage_date` לפי `Asia/Jerusalem`.
5. השרת קורא לפונקציה האטומית במסד הנתונים כדי לשריין שימוש.
6. אם המכסה מוצתה, מוחזרת שגיאת מכסה; לא מתבצעת קריאה ל־OpenAI.
7. אם השימוש אושר, השרת שולח ל־OpenAI הוראות בעברית ונושא הבדיחה. מפתח ה־API נשלף ממשתנה סביבה בצד השרת.
8. השרת מאמת שהתקבלה תוצאה טקסטואלית שאינה ריקה ומחזיר אותה ללקוח.
9. ה־Frontend מסיר את חיווי הטעינה ומחליף את הבדיחה המוצגת בתוצאה החדשה.
10. במקרה של כשל, ה־Frontend מציג הודעת שגיאה ואפשרות מפורשת לנסות שוב. הניסיון החדש עובר שוב את בדיקת המכסה.

### 6.3 קריאה ל־OpenAI

- להשתמש ב־OpenAI SDK הרשמי ל־JavaScript/TypeScript וב־API המתועד העדכני.
- לבצע את הקריאה רק ב־Route Handler בצד השרת.
- להשתמש במזהה המודל שאושר עבור דרישת GPT-5. לשמור אותו במשתנה סביבה, למשל `OPENAI_MODEL`, כדי שלא לקבע מזהה ישן בקוד; ערך ברירת המחדל בפריסה חייב להיות מזהה GPT-5 מאומת וזמין.
- להגדיר `max_output_tokens` נמוך וסביר, משום שנדרשת בדיחה קצרה בלבד.
- להגדיר timeout ולטפל בשגיאות רשת, rate limits ושגיאות ספק.
- הוראות המודל צריכות לקבוע שהפלט יהיה בדיחה בעברית, קשורה לנושא אם הוזן, וכללית אם לא הוזן.
- אין להחזיר למשתמש מידע אבחוני של ספק ה־AI, ואין להפעיל ניסיון חוזר אוטומטי בלתי מוגבל.

## 7. Authentication, Authorization ואבטחה

### 7.1 התחברות

- שיטת ההתחברות היחידה היא Google OAuth באמצעות Supabase Auth.
- מסכים ונתיבי יצירת בדיחה מוגנים: משתמש שאינו מחובר מועבר למסך ההתחברות.
- יש להגדיר ב־Supabase Auth את כתובת האתר ואת רשימת ה־Redirect URLs עבור Development ו־Production.
- יש להשתמש ב־Supabase SSR helpers המתאימים ל־Next.js לניהול session ב־cookies מאובטחים.
- ה־Backend חייב לאמת session בכל בקשת יצירה. אין להסתמך על מזהה משתמש שמגיע בגוף הבקשה.

### 7.2 הרשאות Database

- להפעיל Row Level Security (RLS) על `daily_usage`.
- כברירת מחדל, אין לתת ללקוח הרשאת `INSERT`, `UPDATE` או `DELETE` על נתוני המכסה.
- רק ה־Backend יוכל להפעיל את פעולת שריון המכסה באמצעות הרשאה ייעודית ומצומצמת.
- אם נעשה שימוש ב־`service_role` לצורך פעולה זו, הוא יישמר בשרת בלבד ולעולם לא יופיע במשתני `NEXT_PUBLIC_*`, בקוד לקוח או ב־Git. עדיף להשתמש במנגנון עם הרשאות מינימליות אם הוא עונה על הצורך.
- ה־Database function תוודא שמזהה המשתמש תואם ל־identity המאומת או תהיה זמינה רק לתפקיד שרת מהימן.

### 7.3 ניהול סודות

- `OPENAI_API_KEY`, סוד Supabase בעל הרשאות שרת וכל סוד OAuth נשמרים רק ב־Environment Variables של סביבת השרת.
- ערכים בעלי קידומת `NEXT_PUBLIC_` נחשבים ציבוריים ואסור להציב בהם סודות.
- `.env.local` משמש לפיתוח בלבד, מחוץ ל־Git; יש לכלול `.env*` ב־`.gitignore` ולהוסיף `.env.example` עם שמות משתנים ללא ערכים.
- אין להדפיס סודות או תוכן רגיש ל־logs.

### 7.4 הגנות נוספות

- לאכוף מכסה ב־Database ולא ב־Frontend בלבד.
- להגביל אורך נושא ולוודא ש־`topic` הוא מחרוזת.
- להחזיר הודעות שגיאה כלליות ללקוח ולשמור פרטים טכניים רק ב־server logs.
- להשתמש ב־HTTPS, cookies מאובטחים, בדיקת `Origin`/CSRF בהתאם לדפוס ה־session, והגדרות CORS מצומצמות אם נדרשות.
- לא להוסיף rate limiting נפרד בגרסה הראשונה מעבר למכסה העסקית, אלא אם מתגלים שימוש לרעה או צורך תפעולי; ניתן להוסיף הגנה נוספת בהמשך בלי לשנות את מודל הנתונים.
- לא לשמור נושאים או בדיחות ב־logs כברירת מחדל. אין ב־PRD דרישת היסטוריה או מדיניות שמירת תוכן.

## 8. PWA, ממשק ו־Offline

- להגדיר Web App Manifest באמצעות מנגנון `manifest` של Next.js, כולל `name`, `short_name`, `start_url`, `display: "standalone"`, צבעי theme ו־icons בגודל הנדרש.
- לוודא שהאתר מוגש ב־HTTPS ושקובצי האייקונים זמינים.
- יש לבדוק התקנה בדפדפנים ניידים תומכים. אפשרויות ההתקנה משתנות בין iOS, Android ודפדפנים.
- Service Worker יתווסף רק אם נדרש לצורך התקנה/עדכון או caching בסיסי; אין לממש יצירת בדיחות Offline.
- אין לשמור בדיחות קודמות ב־local storage או ב־IndexedDB. ניתן להשאיר בזיכרון הממשק את הבדיחה הנוכחית בלבד.
- יש להגדיר `lang="he"` ו־`dir="rtl"`, ולוודא שהודעות טעינה, שגיאה ומכסה בעברית.

## 9. Environments, GitHub ו־Deployment

### 9.1 סביבות נפרדות

יש להשתמש בשני פרויקטים נפרדים ב־Supabase:

1. **Development:** משמש לפיתוח ולבדיקות. סביבת הפיתוח המקומית מחוברת לפרויקט זה בלבד.
2. **Production:** מכיל את נתוני המשתמשים האמיתיים של האתר החי. פרטי הגישה אליו נשמרים רק ב־Vercel ובמערכת הפריסה המאובטחת; אין להורידם לסביבת הפיתוח המקומית.

גם ב־Vercel יש להגדיר משתני Environment לפי סביבה. סודות Production יהיו מוגדרים רק עבור Production. ערכי Development של Vercel, אם נדרשים, יפנו לפרויקט Supabase Development ולא ל־Production.

**דוגמת משתנים**
- `NEXT_PUBLIC_SUPABASE_URL` — כתובת הפרויקט המתאים לסביבה.
- `NEXT_PUBLIC_SUPABASE_ANON_KEY` או publishable key — מפתח לקוח ציבורי לפי תצורת Supabase.
- `SUPABASE_SERVICE_ROLE_KEY` או מפתח שרת מצומצם — רק אם נדרש בצד השרת.
- `OPENAI_API_KEY` — סוד OpenAI בצד השרת.
- `OPENAI_MODEL` — מזהה מודל GPT-5 שאושר.
- `APP_TIME_ZONE=Asia/Jerusalem` — אזור הזמן העסקי.
- `NEXT_PUBLIC_APP_URL` — כתובת האפליקציה בסביבה הרלוונטית, אם נדרשת בקוד.

אין לשמור את מפתחות Production בקובץ מקומי, ב־GitHub או ב־`.env.local` של הפיתוח. כתובות ומפתחות ציבוריים אינם תחליף להגדרת RLS והרשאות.

### 9.2 Git ו־Build

- כל קוד המקור וקובצי `supabase/migrations/` נשמרים ב־Git Repository ב־GitHub.
- חיבור ה־Repository ל־Vercel מאפשר Preview Deployment לענפים/בקשות מיזוג ו־Production Deployment מהענף הראשי, לפי הגדרות הפרויקט.
- כל שינוי קוד עובר Build ובדיקות אוטומטיות. אין לפרוס גרסה אם ה־Build נכשל.
- משתני סביבה מוגדרים ב־Vercel לפי הסביבה ואינם נשמרים ב־Repository.
- יש להגדיר בדיקות בסיסיות עבור התחברות, מכסה, יצירה, שגיאות ו־RTL. בדיקות אינטגרציה מול OpenAI צריכות להיות מוגבלות כדי למנוע עלויות מיותרות; אפשר להשתמש ב־mock בבדיקות יחידה.

### 9.3 Database Migrations — נוהל מחייב

שינויים בסכימת Database ינוהלו באמצעות קובצי SQL ב־`supabase/migrations/`, הנשמרים ב־GitHub.

1. יוצרים Migration file ומתעדים בו שינוי סכימה בלבד, או שינוי Database נוסף שניתן לשחזר באופן מבוקר.
2. מריצים ובודקים את ה־Migration מול פרויקט Supabase **Development בענן**. אין דרישה מהמשתמש להתקין Docker או להריץ Supabase מקומי.
3. בודקים את האפליקציה מול Development: התחברות, יצירה, מכסה, מקרי קצה ותאימות הקוד לסכימה.
4. לאחר שהבדיקות עברו, מציגים למשתמש את השינוי ומבקשים אישור מפורש לפני שינוי Production.
5. לאחר אישור, **אחראי הפריסה/המפתח שמנהל את ה־Repository** מריץ את אותו Migration מול פרויקט Production באמצעות תהליך מבוקר של Supabase CLI/CI. אין להפעיל אותו אוטומטית לפני אישור המשתמש.
6. רק לאחר שה־Migration ב־Production הושלם בהצלחה, מתבצע Production Deployment של גרסת האפליקציה שתלויה בסכימה החדשה.
7. אם ה־Migration נכשל, עוצרים את פריסת האפליקציה ומטפלים בכשל לפני ניסיון נוסף.
8. אין לבצע שינויי סכימה ידניים ב־Production דרך Dashboard/SQL Editor לאחר שהתחיל שימוש ב־migrations. במקרה חירום, יש לתעד ולסנכרן את השינוי עם היסטוריית ה־migrations לפני המשך עבודה.

לצורך יישום נוח למשתמש שאינו מתכנת, תהליך האישור וההרצה יכול להתבצע על ידי כלי הפיתוח/AI או איש הפיתוח, אך לעולם לא באמצעות שימוש בפרטי Production מהמחשב המקומי. תהליך ה־Deployment חייב להיות מסודר כך שעדכון מסד הנתונים קודם לגרסת האפליקציה שדורשת אותו.

### 9.4 הגדרות שאינן עוברות ב־Database Migrations

יש להגדיר ולבדוק בנפרד בכל אחד משני פרויקטי Supabase:

- ספק Google OAuth, Client ID/Secret, כתובות Callback ו־Redirect allowlist.
- כתובות אתר ו־Site URL של Auth.
- סודות ו־API keys.
- הגדרות פרויקט, הרשאות משתמשים, ותפקידי גישה.
- הגדרות שירותי Supabase שאינן מוגדרות במפורש כקוד או כ־config בפרויקט.
- הגדרות Billing, Limits ו־Compute.
- משתני Environment ב־Vercel.
- הגדרות Google Cloud OAuth (Origins ו־Redirect URIs) בהתאם לכתובות הסביבות.

אפשר לנהל חלק מהגדרות Supabase באמצעות קובצי config או CI, אך אין להניח ש־SQL migrations מעבירות סודות או הגדרות ספק חיצוני. יש לוודא בפועל שכל סביבה מוגדרת כראוי.

### 9.5 עלויות ומגבלות תוכניות

- **Supabase Free:** לפי תיעוד Supabase העדכני, התוכנית כוללת שני פרויקטים חינמיים פעילים לכלל הארגונים שבהם המשתמש Owner/Admin. פרויקטים Free עם פעילות נמוכה עשויים להיות מושהים אוטומטית לאחר כשבעה ימים; החזרה לפעילות עשויה לדרוש הפעלה מחדש. לכן שני פרויקטים אפשריים לפיתוח ראשוני, אך יש לתכנן תוכנית בתשלום עבור Production שדורש זמינות רציפה.
- **Supabase בתשלום:** לכל פרויקט יש משאבי Compute ועלות משלו, בנוסף לתוכנית הארגון ולשימוש משתנה. יש לבדוק את המחיר העדכני לפני בחירת התוכנית.
- **Vercel Hobby:** התוכנית החינמית מיועדת לשימוש אישי ולא מסחרי. אם המוצר מופעל כשירות מסחרי או עסקי, יש לבחור תוכנית שמתירה שימוש זה, בדרך כלל Pro.
- **OpenAI API:** העלות תלויה במודל ובכמות ה־input/output tokens. בדיחה קצרה צפויה להשתמש במעט tokens, אך יש להגדיר תקציב והתראות ולוודא את התמחור המדויק של מזהה המודל שנבחר.

## 10. Configuration, Observability וטיפול בתקלות

- בעת עליית השרת יש לוודא שמשתני הסביבה הנדרשים קיימים; אם חסר סוד חובה, יש להיכשל בצורה ברורה ב־startup ולא לחשוף ערכים.
- ה־logs צריכים לכלול request ID, תוצאת פעולה כללית, זמן תגובה וקוד שגיאה, אך לא מפתחות, access tokens או תוכן בדיחה/נושא כברירת מחדל.
- יש להפריד בין שגיאת אימות, מכסה שמוצתה, שגיאת OpenAI, timeout ושגיאת Database.
- אין להציג למשתמש שגיאות פנימיות. כל הודעות ה־UI בעברית.
- יש להגדיר התראות שימוש/חיוב ב־OpenAI ובשירותי Hosting/Database לפי האפשרויות הזמינות בתוכנית.
- במקרה של אובדן חיבור לאינטרנט, הממשק מציג הודעה ואפשרות לנסות שוב לאחר חזרת החיבור. אין להציג תוצאה ישנה כאילו נוצרה כעת.

## 11. בדיקות וקריטריוני תקינות ארכיטקטוניים

יש לכסות לפחות את המקרים הבאים:

- משתמש לא מחובר אינו יכול ליצור בדיחה, גם אם הוא שולח בקשת API ישירות.
- התחברות Google מוצלחת מחזירה את המשתמש למסך יצירת הבדיחות; כשל התחברות מציג הודעה ואפשרות לנסות שוב.
- נושא מלא מייצר בדיחה בעברית הקשורה לנושא; נושא ריק מייצר בדיחה כללית בעברית.
- כל תוצאה חדשה מחליפה את הבדיחה הקודמת, ואין היסטוריה שמורה.
- לאחר 10 בקשות שאושרו לאותו יום בישראל, בקשות נוספות נדחות ולא מתבצעת קריאת OpenAI.

- המכסה מתאפסת בחצות `Asia/Jerusalem`, כולל בדיקות מעבר בין שעון קיץ לשעון חורף.
- כשל OpenAI או ניתוק רשת מציג הודעה בעברית ואפשרות מפורשת לנסות שוב.
- מפתחות OpenAI וסודות שרת אינם נחשפים בקוד לקוח, בקובצי Git או בתגובות API.
- סביבת Development אינה קוראת או כותבת ל־Database של Production.
- Migration נבדק ב־Development ומאושר לפני הרצה ב־Production; פריסת קוד שתלויה בשינוי סכימה אינה מקדימה את ה־Migration.
